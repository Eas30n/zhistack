# 秒杀压测对照实验（ZhiStack Benchmark）

## 实验设计

- 场景：一场线下沙龙放出 **137 张免费票**，**1000 个用户并发抢票**（JMeter，ramp-up 10s，每用户 1 请求）
- 对照组 A（无防护）：`/benchmark/seckill-no-guard/{id}` —— 教科书新手写法（查库存→判重→扣减→下单，全程无并发保护），**刻意保留用于演示超卖**
- 对照组 C（生产实现）：`/ticket-order/seckill/{id}` —— Redis 库存 + Lua 原子预校验（库存/一人一单）+ 订单号预生成 + Redis Stream 异步落库

## 复现步骤

```bash
# 前置：后端 8081、Redis 6379、MySQL 3306(zhistack 库)、1000 个测试 token
bash gen-tokens.sh          # 注册测试用户并导出 tokens.csv
bash run-benchmark.sh A     # 跑无防护组
bash run-benchmark.sh C     # 跑生产实现组
```

每组输出 `results/<组>/report/index.html`（JMeter HTML 报告：吞吐、P99、错误率）与 `summary.txt`。

## 校验口径

| 指标 | 含义 | 期望 |
|---|---|---|
| success | 接口层抢票成功数 | ≤ 库存 |
| db_orders | 订单表实际行数 | = success |
| duplicate_orders | 同一用户重复下单数 | = 0 |
| db_stock_left | 剩余库存 | ≥ 0（A 组会打穿成负数） |

## 结果（2026-10-17 实测，137 票 / 1000 并发 / ramp-up 10s）

| 组 | requests | 落库订单 | 重复下单 | 剩余库存 | 平均RT | 中位RT | P99 | 错误率 |
|---|---|---|---|---|---|---|---|---|
| A 无防护 | 1000 | **997（超卖 860）** | 0 | 17（丢失更新） | 2235ms | 2050ms | 4931ms | 0.3% |
| C Lua+Stream | 1000 | **137（=库存）** | 0 | 0 | 1642ms | **1207ms** | 4562ms | 0% |

## 结论

1. **A 组超卖实锤**：137 张票落库 997 单，"查询-判断-执行"三步在 1000 并发下全部失效；同时库存字段只扣到 17（读-改-写互相覆盖，丢失更新）；
2. **C 组零超卖**：Lua 把库存判断与扣减收敛为 Redis 单线程原子操作，**MySQL 写请求从 1000 降到 137**——只有真实抢到票的用户才产生订单消息；
3. **异步化收益**：C 组中位响应 1207ms，比同步写库路径的 A 组快 41%，且 0 错误（A 组有 3 个请求超时）；
4. 附注：压测中还发现 Stream 消费者在消费者组丢失（NOGROUP）时会异常风暴而非自愈重建，属于后续改进项。

## 环境说明

家用单机（Windows + 单实例 MySQL/Redis），数字用于**组间相对比较**，不代表生产容量。
